# 사고 대응 (incident)

## 사고의 범위

- 의도하지 않은 주문 (중복·금액 초과·잘못된 종목·사용자 보유분 매도)
- 장부 ↔ 계좌 불일치로 인한 정지
- 키·개인정보 노출 (커밋·로그·스크린샷)
- 데이터 오류로 인한 잘못된 판단 (결측 캔들, 김치 프리미엄 혼동 등)
- dry-run 에서 발견했더라도 **실거래였으면 돈이 나갔을 버그**는 사고로 기록한다 (near-miss)

## 대응 순서

1. **멈춘다** — 킬 스위치. 원인 파악 전에 재개하지 않는다
2. **피해를 막는다** — 미체결 주문 확인, 키 노출이면 키 폐기·재발급이 먼저
3. **사실을 확정한다** — 장부·주문 기록·거래소 내역 대조. 추측 금지
4. **재현 테스트** — 실패하는 테스트를 먼저 쓴다
5. **고친다** — 테스트 통과 + 같은 종류의 다른 경로도 점검
6. **기록한다** — `docs/incidents/YYYY-MM-DD-<slug>.md` (`incident` 스킬)
7. **재발 방지** — 새 방어선(테스트·가드·룰)을 추가. 룰이 바뀌면 `.claude/rules/` 도 갱신

## 템플릿

```markdown
# YYYY-MM-DD — <slug>

- 상태: open / mitigated / resolved
- 심각도: S1 실제 손실 / S2 손실 가능했음(near-miss) / S3 운영 불편
- 모드: live / dry-run

## 요약
## 타임라인 (UTC 와 로컬 병기)
## 영향 (금액은 예산 대비 % 로도 표기)
## 원인
## 대응
## 재발 방지
- [ ] 테스트:
- [ ] 가드/룰:
```

`docs/incidents/` 는 로컬 전용 — 실제 금액을 적어도 된다. 공개 PR·커밋에는 금액 없이 "장부 대조 누락 수정" 수준으로만.
